## Context

ADR 0036은 Tauri 앱 **SIW Agent**가 승인된 전략을 실행하고, 주문은 단계별 Gate로 넓힌다고 정했다. 단계 1은 모의투자 주문만이고, 이 ADR은 그 설계다.

**2026-10-23 사용자 범위 변경:** "모의투자는 키움증권도 할 수 있게 해줘. KIS는 현재 API를 등록 못한 상태야."

- 지금 실제로 쓸 수 있는 첫 증권사는 **키움**이다.
- 한국투자(KIS)는 같은 주문 계약 뒤의 두 번째 adapter로 설계에 남긴다.
- ADR 0036도 같은 PR에서 고친다.

**2026-10-23 사용자 결정:** "첫 시장 미국".

- 단계 1의 첫 시장은 미국 주식이다. 키움 미국 주문 api-id `ust20000`~`ust20003`을 모의 도메인 `mockapi.kiwoom.com`으로 보낸다.
- 키움 모의 서버가 미국 주문을 받는지는 여전히 미검증이다. 그래서 구현의 첫 단계(P0)는 주문이 아닌 조회 1회로 이를 확인하는 것이다(9절).

**2026-10-23 사용자 답변(미결 질문):**

1. 주문 유형: 지정가와 시장가를 모두 허용한다.
2. 한도: 1건 주문 금액 100만 원. 일 주문 수, 일 손실률, 종목 수는 우선 제한하지 않고 나중에 적용한다.
3. 킬 스위치: 신규 주문만 중지한다.
4. 실행 시간: 상주.

6. P0 승인.

### 현재 코드에서 확인한 사실

- **키움 연동은 조회 전용이다.**
  - 시세: `services/market_data/kiwoom.py`.
  - 계좌: `services/market_data/kiwoom_account.py`. `AllowlistedClient`가 토큰과 조회 api-id 3개(`ust21150`, `kt00015`, `ust21100`)만 허용한다.
  - 두 모듈 모두 모의 도메인 `DEMO_BASE_URL = "https://mockapi.kiwoom.com"`과 실전 `https://api.kiwoom.com`을 안다. 키 등록의 계좌 환경(`real`/`demo`)으로 둘 중 하나를 고른다.
  - 키움 접근 토큰은 계좌 하나에 묶인다(ADR 0029). 계좌번호를 읽거나 저장하지 않고, 계좌는 앱 키 해시로 가리킨다.
- **KIS 연동도 조회 전용이다.**
  - `services/market_data/kis.py`는 해외주식 분봉만 읽는다.
  - 모의 도메인 `DEMO_BASE_URL = "https://openapivts.koreainvestment.com:29443"`(공식 open-trading-api의 `vps`)이 있다.
  - 사용자는 지금 KIS API를 등록하지 못한 상태다.
- **계좌 환경은 키에서만 온다.** 키 등록에서 정한 환경만 쓰고, 프로세스 환경변수로 바꿀 수 없다(`services/credentials/catalog.py`).
- **원장은 넷이다.**
  - 저널 저장소: 수동 실제 체결, 거래내역서 가져오기, 증권사 API(`broker_api`, ADR 0018), 가상 시나리오.
  - 백테스트 체결: `backtests.sqlite3`에만 있다(ADR 0021).
- **전략은 불변 버전이다.** 버전마다 정의와 SHA-256이 있다. Python 전략은 격리 프로세스에서 봉 하나씩 받는다(ADR 0021).
- **Tauri 앱은 API를 띄우지 않는다.** `src-tauri/src/lib.rs`는 창만 연다. Electron은 저장소를 찾아 `uv run uvicorn`을 띄운다(ADR 0028).
- **두 앱은 같은 화면 빌드(`apps/desktop/dist`)를 쓴다.**

### 키움 공식 스펙에서 확인한 것

kiwoom-spec MCP 서버(공식 REST 스펙 색인, 읽기 전용)의 `spec_search`·`spec_show`로 확인했다. 키움 API는 호출하지 않았다.

- **도메인:** 모든 API 페이지에 "운영 도메인 `https://api.kiwoom.com`"과 "모의투자 도메인 `https://mockapi.kiwoom.com`"이 함께 적혀 있다. 국내 주문, 미국 주문, 토큰 발급(`au10001`) 모두 같다.
- **실전과 모의의 구분은 도메인뿐이다.** api-id는 실전과 모의가 같다. KIS처럼 모의 전용 TR ID(`V…`)가 없다.
- **주문 api-id:**

  | 시장            | 매수       | 매도       | 정정       | 취소       | 경로                   |
  | --------------- | ---------- | ---------- | ---------- | ---------- | ---------------------- |
  | 국내 주식(현금) | `kt10000`  | `kt10001`  | `kt10002`  | `kt10003`  | `POST /api/dostk/ordr` |
  | 미국 주식       | `ust20000` | `ust20001` | `ust20002` | `ust20003` | `POST /api/us/ordr`    |

  신용 주문(`kt10006`~`kt10009`, `/api/dostk/crdordr`)과 금현물(`kt5000x`)은 단계 1 범위 밖이다.

- **국내 주문 요청:**
  - `dmst_stex_tp`: `KRX`/`NXT`/`SOR`.
  - `stk_cd`, `ord_qty`(1주 단위), `ord_uv`(원).
  - `trde_tp`: 0 보통(지정가), 3 시장가, IOC·FOK, 시간외, 스톱지정가 등.
  - 응답은 `ord_no`(7자리)와 거래소 구분뿐이다. 체결 정보는 없다.
- **미국 주문 요청:**
  - `stex_tp`: `NA` AMEX, `ND` NASDAQ, `NY` NYSE.
  - `stk_cd`, `ord_qty`, `ord_uv`.
  - `trde_tp`: 00 지정가, 03 시장가, 26/27 VWAP·TWAP 지정가, 30 LOC, 36/37 VWAP·TWAP 시장가.
  - 응답은 `ord_no`(9자리)와 외화예수금·사용증거금 등이다.
- **요청 본문에 계좌번호 칸이 없다.** 계좌는 토큰으로 정해진다. 그래서 키움은 계좌번호를 다루지 않고 모의 주문을 낼 수 있다.
- **주문·체결 조회:**
  - 국내: `kt00007` 계좌별주문체결내역상세, `kt00009` 계좌별주문체결현황.
  - 미국: `ust21510` 당일 주문체결 확인. 주문·체결 수량, 체결단가, 주문·응답·체결 시각(`HH:mm:ss`), 상태가 온다. 과거 날짜는 `ust21150`.
  - 실시간: 국내 `00` 주문체결, 미국 `F4` 실시간 주문 확인(WebSocket).
- **잔고 조회:** 국내 `kt00018` 계좌평가잔고내역, `kt00001` 예수금. 미국 `ust21070` 원장잔고확인.
- **주문 가능 수량:** 국내 `kt00010`·`kt00011`, 미국 `ust31490`.

**키움 문서만으로 알 수 없고 계정으로 확인하지 않은 것(`unverified`):**

- **모의 서버가 미국 주식 주문을 받는지.** 모든 페이지가 같은 틀로 모의 도메인을 적고 있다. 모의투자 지원 범위를 따로 설명하는 페이지는 색인에 없다("모의투자"·"모의" 검색 결과 0건). 그래서 미국 주문 페이지에 모의 도메인이 적혀 있다는 사실만으로 미국 모의 주문이 된다고 보지 않는다.
- 모의 서버가 받는 미국 `stex_tp`·`trde_tp` 범위(국내라면 `dmst_stex_tp`의 NXT·SOR), 장 시간 밖 주문 처리.
- 모의 호출 한도, 모의 체결 방식(시세 기준인지, 부분 체결이 있는지), 체결 시각의 의미.
- 모의 키가 실전 키와 따로 발급되는지, 모의 계좌의 초기 자금.

### KIS 문서 기준 사실(미검증)

- 모의투자는 실전과 다른 앱 키·계좌를 쓴다.
- 주문 TR ID가 실전 `T…`, 모의 `V…`로 갈린다(예: 국내 현금주문 `TTTC0012U` ↔ `VTTC0012U`).
- 주문 요청에 계좌번호(종합계좌 8자리 + 상품코드 2자리)가 들어간다.
- 모의 호출 한도가 실전보다 낮다.

## Decision

### 0. 증권사 중립 구조

- 주문 의도·원장·한도·킬 스위치·실행기는 증권사와 무관하다.
- 증권사별 차이는 adapter 하나에 모은다.
  - `services/paper_trading/brokers/kiwoom_paper.py`: 단계 1에서 먼저 구현한다.
  - `services/paper_trading/brokers/kis_paper.py`: 사용자가 KIS 키를 등록한 뒤 구현한다.
- adapter의 기능은 다음뿐이다.
  - `submit(intent) -> SubmissionResult`, `cancel(order_ref)`.
  - `order_status(since)`, `balances()`.
  - `capabilities()`: 이 adapter가 받는 시장과 주문 유형.
- 한 실행 승인은 증권사 하나, 모의 계좌 하나만 쓴다. 두 증권사의 모의 원장은 같은 표에 두되 `broker_id`와 계좌 참조로 나누고, 합산해서 보여 주지 않는다.

### 1. 모의 주문 원장: 기존 원장과 분리

- **저장소:** `SIW_DATA_DIR/paper_orders.sqlite3`. 저널(`journal.sqlite3`)과 백테스트 저장소에 넣지 않는다. 번호 기반 migration을 쓴다.
- **원장 유형:** `broker_paper`(증권사 모의투자 체결). 행마다 `broker_id`(`kiwoom`/`kis`)가 있다. 기존 4개 원장 유형과 백테스트 체결 중 어느 것과도 합산하지 않는다.
  - 대사(ADR 0025), 매매 복기 Agent의 실제 체결(ADR 0022), 브로커 원장 포지션 계산은 이 원장을 읽지 않는다. 테스트로 확인한다.
  - 차트에 그릴 때는 백테스트 `BT`처럼 별도 마커(예: `PAPER`)와 "모의 체결" 칩을 쓴다. 실제 체결 마커와 같은 모양으로 그리지 않는다.
- **표(초안):**
  - `order_intents`: 주문 의도(2절). 추가만 하고 고치지 않는다.
  - `order_submissions`: 의도 1건에 제출 시도 1건. 담는 내용:
    - `broker_id`, 계좌 참조.
    - 요청 시각, 응답 시각, 증권사 주문번호, 응답 코드·메시지(200자 이내).
    - 상태: `pending_response → accepted | rejected | unknown`.
  - `paper_executions`: 모의 주문·체결 조회로 받은 체결.
    - 조회 응답이 주는 단위 그대로 저장한다. 건별 체결이 아니면 ADR 0018처럼 `granularity: order_aggregate`로 표시한다.
    - 시각의 의미(`time_meaning`)를 기록하고, 응답에 없는 체결 순서나 시각을 만들지 않는다. 키움 시각은 날짜 없는 `HH:mm:ss`라서, ADR 0029처럼 날짜와 시간대를 정하는 규칙을 쓰고 정하지 못하면 `time_unresolved`로 둔다.
    - `fill_origin: broker_demo_simulated`로 시장 체결이 아님을 표시한다.
  - `limit_events`·`kill_switch_events`: 한도 거절, 킬 스위치 켜기·끄기, 재무장(arm) 기록.
- **금액·수량:** Decimal 문자열. 통화(KRW/USD)는 원장 행마다 둔다.
- **계약(신규, JSON Schema 2020-12):** `paper_order_intent`, `paper_order_submission`, `paper_execution`, `paper_runner_status`. Python·TypeScript validator, fixture, 생성 타입을 같은 작업에서 추가한다.

### 2. 주문 의도(order intent) 계약

전략 신호가 주문이 되기 전에 반드시 의도 1건을 기록한다. 기록하지 못하면 주문하지 않는다. 의도는 증권사와 무관하다.

- **식별:**
  - `intent_id`: `sha256(approval_id, strategy_version, instrument_id, side, signal_bar_start_utc)`에서 만든다. 같은 신호는 재시작 뒤에도 같은 ID라서 두 번 제출되지 않는다.
  - `created_at_utc`.
- **실행 대상:** `broker_id`, 계좌 참조, `environment: demo`(다른 값은 스키마가 거부).
- **전략:**
  - `strategy_id`, `strategy_version`, `definition_sha256`.
  - `approval_id`: 3절의 실행 승인 기록.
  - `strategy_kind`(`rules`/`python`). Python이면 샌드박스 출력 `logs`의 해시도 둔다.
- **데이터 시점(cutoff):**
  - `data_as_of_utc`: 판단에 쓴 데이터의 기준 시각.
  - `signal_bar_start_utc`/`signal_bar_end_utc`, 그리고 `signal_bar_final: true`. 확정되지 않은 봉이면 의도를 만들지 않는다.
  - 봉 출처 묶음: `source_id`, `feed_scope`, `dataset_revision`, `adjustment`, 세션, 입력 봉 개수와 SHA-256(ADR 0021 입력 고정과 같은 방식).
  - 거래소 현지시간과 캘린더 ID·버전.
  - 신호 데이터 출처와 주문 증권사가 다르면(예: 미국 시세는 Alpaca, 주문은 키움 모의) 둘 다 기록한다.
- **신호 근거:**
  - 규칙 전략: 평가한 조건 트리와 각 피연산자 값(지표 ID·파라미터·출력·값).
  - Python 전략: `ctx.buy/sell` 호출 내용과 그 봉의 지표 값.
  - 근거는 값과 출처만 담는다. 해설(Agent 추론)은 따로 두고 섞지 않는다.
- **수량·가격 계산:**
  - `sizing_method`(`shares`/`cash`/`percent_equity`)와 입력값.
  - 계산에 쓴 기준 자산·현금(모의 원장 기준, 시각 포함), 기준 가격과 그 출처(예: 신호 봉 종가), 수수료 가정, 내림 규칙.
  - 결과 `quantity`.
  - `order_type`: `limit`(지정가) 또는 `market`(시장가). 사용자 결정으로 둘 다 허용한다.
    - 지정가: 지정가와 그 계산식(예: 기준가 × (1 + 허용 bp), 호가 단위 내림)을 남긴다.
    - 시장가: 체결가를 미리 알 수 없다. 주문 금액 한도 검사에 쓰는 **추정 상한가**(기준가 × (1 + 시장가 버퍼 bp))와 기준가의 출처·시각을 남긴다. 기준가가 일정 시간보다 오래됐으면 주문하지 않는다.
  - 증권사 코드로 바꾸는 일(키움 미국 지정가 `00`·시장가 `03`, 국내 `0`·`3`)은 adapter가 하고, 바꾼 값을 제출 기록에 남긴다.
  - 키움 모의 서버가 미국 시장가(`03`)를 받는지는 미검증이다. P4에서 지정가로 먼저 확인한 뒤 시장가를 연다.
- **한도 검사 결과:** 검사한 한도 값과 통과·거절 사유(5절).
- **상태:** `recorded → submitted | blocked(사유) | expired`.
  - 신호 봉 다음 거래 세션 안에 제출하지 못하면 `expired`로 두고 나중에 몰아서 제출하지 않는다.

**백테스트와의 차이:** 백테스트는 다음 봉 시가에 체결된다고 가정한다(ADR 0021). 모의 주문은 신호 봉이 확정된 뒤 제출하므로 체결가가 다르다. 의도에 기준 가격을 남겨, 화면에서 "백테스트 가정가 대비 모의 체결가" 차이를 보여 준다. 이것은 참고 지표이고 실거래 성과를 보장하지 않는다.

### 3. 전략 입력과 실행 승인

- SIW Agent는 Research에서 저장한 전략 버전만 실행한다. 실행 단위는 `strategy_id@version` + `definition_sha256`으로 고정한다.
- **실행 승인 기록(`approval_id`):** 사용자가 SIW Agent 화면에서 다음을 보고 승인한다. 승인 시각과 내용 해시를 저장한다.
  - 전략 버전, 대상 종목, 한도.
  - 증권사와 모의 계좌 참조.
- 다음 경우에는 새 승인이 필요하다.
  - 전략 버전, 종목, 한도, 증권사, 계좌 중 하나라도 바뀐다.
  - Agent가 만든 전략 코드다(기존 규칙). 이때는 코드 검토 승인이 먼저 있어야 한다.
- Python 전략은 백테스트와 같은 샌드박스(빈 환경변수, 네트워크 차단 감사 훅, 봉 하나씩 전달)에서 돈다. 전략 코드는 키·토큰·주문 클라이언트에 닿지 않는다. 전략은 의도만 돌려주고, 제출은 실행기가 한다.

### 4. 실계좌 도메인 차단(코드, 두 증권사 공통)

실계좌 주문은 단계 2 승인 전까지 호출할 수도 시험할 수도 없게 만든다. 설정으로 열 수 있는 길을 두지 않는다. 키움은 실전과 모의가 도메인으로만 갈리므로, **host 검사가 유일하고 결정적인 차단선**이다.

- **별도 모듈:** 주문 adapter는 `services/paper_trading/brokers/`에 둔다.
  - 시세·계좌 모듈(`kiwoom.py`, `kiwoom_account.py`, `kis.py`)의 `REAL_BASE_URL`, `base_url` 설정, `SIW_*_BASE_URL`을 가져오지도 재사용하지도 않는다.
  - 조회 전용 모듈의 허용목록에는 주문 api-id를 넣지 않는다(지금 그대로).
- **도메인 상수 고정:** adapter마다 모의 도메인 상수 하나만 있다.
  - 키움: `https://mockapi.kiwoom.com`.
  - KIS: `https://openapivts.koreainvestment.com:29443`.
  - 생성자에 URL 인자가 없다(테스트는 `transport`만 바꾼다).
- **요청마다 검사:** 공용 `PaperOnlyClient`가 요청 직전에 실제 요청 URL의 scheme·host·port를 그 adapter의 모의 도메인과 비교한다. 다르면 `LiveDomainBlockedError`를 던지고 아무것도 보내지 않는다. 리다이렉트는 따르지 않는다.
- **api-id·TR ID 허용목록:** 경로와 api-id를 쌍으로 허용한다.
  - 키움: 토큰 `au10001`.
    - 미국(첫 시장): 주문 `ust20000`·`ust20001`·`ust20003`, 조회 `ust21070`·`ust21510`·`ust21150`. `ust31490`은 모의투자에서 제공되지 않아(P0) 넣지 않는다. 주문 api-id는 P0에서 모의 지원을 확인한 뒤에만 허용목록에 넣는다.
    - 국내는 미국 대신 국내로 시작하기로 정할 때만 넣는다: 주문 `kt10000`·`kt10001`·`kt10003`, 조회 `kt00007`·`kt00009`·`kt00018`·`kt00001`.
    - 신용(`/api/dostk/crdordr`)과 금현물은 넣지 않는다. 정정(`ust20002`)은 필요할 때 따로 추가한다.
  - KIS: 주문·취소·조회 TR ID가 모두 `V`로 시작해야 하고, `T`로 시작하는 TR ID는 거부한다. 해시키는 문서상 필요하면 넣는다.
- **키 환경 검사:** 키 등록에서 환경이 `demo`인 키만 주문 adapter에 넘긴다. `real` 키를 넘기면 생성 단계에서 거부한다.
- **정적 검사:** `verify.sh`에 검사를 추가한다. `services/paper_trading/`에 다음이 나타나면 실패한다.
  - 실전 도메인 문자열(`api.kiwoom.com`, `openapi.koreainvestment.com:9443`).
  - `T`로 시작하는 KIS 주문 TR ID.
  - 시세·계좌 모듈의 실전 상수 import.
  - `mockapi.kiwoom.com`과 `api.kiwoom.com`은 접두어만 다르므로, 검사는 host 전체를 정확히 비교한다.

### 5. 한도와 킬 스위치

**한도:** 실행 승인에 포함되는 값이다. 제출 직전에 코드에서 검사하고, HTTP 요청보다 먼저 한다. 사용자가 "우선 없음"으로 정한 한도도 코드와 승인 기록에는 칸을 두고 값을 `null`(제한 없음)로 저장한다. 나중에 값을 넣으면 바로 적용할 수 있다.

| 한도        | 단계 1 값(사용자 결정) | 내용                                                                                    |
| ----------- | ---------------------- | --------------------------------------------------------------------------------------- |
| 주문 금액   | **1건 100만 원**       | 지정가는 수량 × 지정가, 시장가는 수량 × 추정 상한가. 원화로 환산해 비교한다(아래)       |
| 종목        | 종목 수 제한 없음      | 실행 승인에 적은 종목만 주문한다(허용목록). 목록의 길이는 제한하지 않는다               |
| 일 주문 수  | 없음(나중에 적용)      | 거래소 현지 날짜 기준 제출 건수 상한                                                    |
| 일 손실     | 없음(나중에 적용)      | 당일 시작 모의 평가액 대비 손실 상한. 값을 넣으면 넘을 때 킬 스위치를 자동으로 켠다     |
| 종목별 보유 | 없음(나중에 적용)      | 종목당 최대 보유 금액·수량                                                              |
| 시장        | 고정 규칙              | adapter의 `capabilities()`에 있는 시장만. 키움 미국 모의는 P0 확인 전까지 없음          |
| 호출 간격   | 고정 규칙              | 모의 호출 한도(문서상 값, 미검증)보다 보수적인 최소 간격                                |
| 미확인 주문 | 고정 규칙              | 응답이 없는(`unknown`) 제출이 1건이라도 있으면 새 주문 금지. 조회로 상태를 맞춘 뒤 재개 |

- **원화 한도와 달러 주문:** 미국 주문 금액은 USD다. 100만 원 한도와 비교하려면 환율이 필요하다.
  - 쓴 환율, 출처, 시각을 의도에 남긴다. 환율을 구할 수 없으면 주문하지 않는다.
  - 환율 출처는 P1에서 정한다(후보: 실행 승인 때 사용자가 확인한 고정 환율, 증권사 조회 응답의 환율). 지금 저장소에는 환율 데이터가 없다.
- **한도 변경:** 한도를 조이면 즉시 적용한다. 늘리거나 없애면 새 실행 승인이 필요하다.
- **보수적 기본값:** 주문 금액을 계산할 기준가나 환율이 없으면 주문하지 않는다. 일 손실 한도를 넣은 뒤에는, 일 손실을 계산할 수 없을 때도 주문하지 않는다.

**킬 스위치:**

- **켜는 방법:**
  - SIW Agent 화면 상단의 항상 보이는 버튼.
  - 메뉴와 단축키.
  - 일 손실 한도를 넣은 뒤에는 그 한도 도달 시 자동.
  - 이상 상태(미확인 주문이 일정 시간 넘게 지속, 데이터 출처·리비전 불일치, 시계 차이) 시 자동.
- **동작:**
  1. `paper_orders.sqlite3`에 정지 상태를 기록한다. 실행기는 제출 직전에 이 상태를 다시 읽는다.
  2. 실행기는 정지 상태를 몇 초마다 읽고, 보면 주문 루프를 멈춘다. 프로세스는 살아 있어 상태와 조회는 계속 보고한다.
  3. 실행기가 응답하지 않으면 SIW Agent(Rust)가 `launchctl`로 실행기 서비스를 내린다(6절). API나 화면이 응답하지 않아도 이 경로로 멈출 수 있다.
  4. **신규 주문만 중지한다(사용자 결정).** 미체결 모의 주문은 취소하지 않고 그대로 둔다. 화면에 미체결 목록을 보여 주고, 취소는 사용자가 주문별로 누른다(모의 도메인으로만 간다).
- **앱 없이 켜기:** SIW Agent가 꺼져 있어도 `uv run python -m services.paper_trading halt --reason …`로 정지 상태를 기록할 수 있다.
- **해제:** 정지 해제만으로는 다시 주문하지 않는다. 사용자가 재무장(arm)해야 하고, 그 기록이 남는다.

### 6. 실행 구조: API와 상주 실행기

**결정:** 실행기는 API와 분리한 **상주** 프로세스다(사용자 결정: 상주). SIW Agent 앱을 꺼도 계속 돈다. macOS의 사용자 LaunchAgent로 둔다.

```
launchd (사용자 LaunchAgent: com.pensivetraveler.siw.agent.runner)
 └─ 실행기 (uv run python -m services.paper_trading.service)   ← 앱과 무관하게 상주
       ├─ 봉 조회 (기존 bar service, 확정 봉만)
       ├─ 전략 평가 (기존 샌드박스)
       ├─ 의도 기록 → 한도 검사 → 증권사 모의 adapter (키움 / KIS)
       ├─ 정지 상태 확인(제출 직전 + 몇 초마다), heartbeat 기록
       └─ paper_orders.sqlite3 (단일 쓰기 주체)

SIW Agent (Tauri, Rust) — 열려 있을 때만
 ├─ 화면 (agent 빌드)  ── HTTP ──▶  API (uvicorn, 127.0.0.1:8765)  ── 읽기: 모의 원장·상태 / 쓰기: 승인·킬 스위치
 └─ launchctl로 실행기 서비스 설치·시작·정지·제거
```

- **설치:** LaunchAgent plist(`~/Library/LaunchAgents/com.pensivetraveler.siw.agent.runner.plist`)는 사용자가 SIW Agent 화면에서 "상주 실행기 설치"를 눌렀을 때만 만든다. 제거 버튼도 둔다. plist에는 저장소 경로와 `SIW_DATA_DIR`만 담고 키는 담지 않는다. 키는 실행기가 키체인에서 읽는다.
- **로그인·재부팅·충돌:** launchd가 로그인 때 실행기를 띄우고, 비정상 종료 때 다시 띄운다.
  - 다시 뜬 실행기는 먼저 재시작 복구(아래)를 끝낸다.
  - 무장 상태와 정지 상태는 DB에 있으므로 그대로 이어진다. 정지돼 있었으면 정지된 채로 뜬다.
  - 재부팅 뒤 자동으로 무장 상태를 이어 갈지는 실행 승인 화면에서 사용자가 고른다. 기본값은 "이어 감"이다.
- **heartbeat:** 실행기는 상태와 마지막 heartbeat 시각을 DB에 쓴다. 화면은 heartbeat가 오래되면 "실행기 응답 없음"을 띄운다.

- **API 기동:** Electron과 같은 규칙을 Rust로 옮긴다(ADR 0028).
  - 127.0.0.1:8765가 이미 응답하면 그 API를 쓴다.
  - 아니면 `SIW_REPO_DIR` → 앱 설정에 저장한 폴더 → 폴더 선택 순으로 저장소를 찾고 `uv run uvicorn`을 띄운다.
  - 자기가 띄운 API만 종료 시 멈춘다. 로그는 `~/Library/Logs/siw-agent/`.
- **실행기 무장:** 실행기 프로세스가 떠 있어도 실행 승인과 무장(arm)이 없으면 주문하지 않는다.
  - 실행기는 `SIW_DATA_DIR`가 없거나 승인한 증권사의 모의 키가 없으면 주문 루프를 시작하지 않는다.
- **분리 이유:**
  - 화면이나 API의 오류·재시작이 주문 루프를 건드리지 않는다. 앱을 꺼도 실행기는 돈다.
  - 주문 adapter와 키 읽기는 실행기 안에만 있다. API에는 주문 엔드포인트가 없다.
  - 킬 스위치는 DB 정지 상태와 `launchctl` 두 경로라서 API에 의존하지 않는다.
- **토큰:** 키움 토큰은 클라이언트 하나에만 유효할 수 있다. 다른 클라이언트가 발급하면 기존 토큰이 바뀐다(ADR 0029, return code 3·8005). 조회 전용 동기화와 실행기가 같은 모의 키를 동시에 쓰지 않게, 모의 키는 실행기만 쓴다.
- **API의 모의 주문 관련 엔드포인트(초안):**
  - 읽기: `GET /v1/paper/status`, `GET /v1/paper/intents`, `GET /v1/paper/executions`.
  - 쓰기: `POST /v1/paper/approvals`, `POST /v1/paper/kill`, `POST /v1/paper/arm`.
  - 쓰기 엔드포인트는 Tauri 출처(`tauri://localhost`)만 받는다. Electron 출처 `siw://app`과 개발 서버 출처는 403이다. 출처 헤더는 로컬 프로세스가 꾸밀 수 있으므로 웹 페이지와 Research 앱을 막는 장치로만 본다. 실제 주문 권한은 실행기에만 있다.
- **재시작 복구:** 실행기는 시작 때 `pending_response`·`unknown` 제출을 증권사 모의 주문 조회로 먼저 맞춘다. 끝나기 전에는 새 주문을 내지 않는다.
- **시각:** 판단과 기록은 UTC로 한다. 세션 판단은 거래소 캘린더로 한다. 로컬 시계와 증권사 응답 시각이 크게 어긋나면 자동 정지한다.

### 7. 화면: SIW Agent와 SIW Research의 차이

**결정:** 빌드를 분리한다. 같은 소스에서 `VITE_SIW_APP=agent|research`로 두 번 빌드하고, Tauri는 `dist-agent`, Electron은 `dist-research`를 싣는다. 실행 중 셸을 감지하는 방식보다 낫다. Research 빌드에는 모의 주문 화면 코드가 아예 들어가지 않기 때문이다.

|         | SIW Agent                                                                            | SIW Research                  |
| ------- | ------------------------------------------------------------------------------------ | ----------------------------- |
| 첫 화면 | 실행 상태판: 실행기 상태, 무장 여부, 킬 스위치(항상 보임), 오늘 주문 수·손익 대 한도 | 지금의 차트 워크스페이스      |
| 전략    | 승인된 버전 목록, 실행 승인 화면(버전·종목·한도·증권사·계좌 참조 확인)               | 작성·수정·백테스트·워크포워드 |
| 주문    | 의도 목록(근거·데이터 시점·계산 펼침), 제출·거절·체결, 백테스트 가정가 대비 차이     | 없음                          |
| 차트    | 실행 종목 차트 + `PAPER` 마커(읽기 위주)                                             | 전체 기능                     |
| 표시    | 상단 띠 "모의투자 — 실제 주문 아님", 증권사 이름과 계좌 참조                         | 주문 기능 없음 표시           |

Research에서 승인된 전략 버전을 "Agent에서 실행"으로 넘기는 연결은 단계 1에 두지 않는다. Agent에서 버전을 직접 고른다.

### 8. 키와 계좌번호

- 이번 설계 작업에서는 키·계좌번호를 다루지 않았다.
- **키움:** 키 등록 화면에서 환경을 `demo`로 한 키움 모의 키(앱 키·시크릿 키)를 쓴다. 지금 키 칸 그대로다. 주문 요청에 계좌번호가 없으므로 계좌번호 칸을 추가하지 않는다. 계좌 참조는 `kiwoom-<sha256(app_key)[:16]>-demo`.
- **KIS:** 주문에 계좌번호가 필요하다(문서 기준). 구현할 때 키 항목에 계좌번호 칸을 비밀 값으로 추가해 키체인에 저장한다. 원장·로그·화면에는 참조와 끝 4자리만 남긴다(ADR 0018과 같은 방식).
- 키 등록은 사용자가 Keys 화면에서 직접 한다.

## P2 구현(2026-10-23, 사용자 승인)

사용자 승인("응 진행해줘")으로 키움 모의 adapter와 실행기의 핵심 루프를 구현했다. 가짜 키움 서버(`httpx.MockTransport`)로만 시험했고, 실제 `mockapi.kiwoom.com` 호출은 없다.

- **`brokers/kiwoom_paper.py`(`KiwoomPaperBroker`):**
  - 허용목록: 토큰 `au10001`, 매수 `ust20000`, 매도 `ust20001`, 취소 `ust20003`, 당일 주문체결 `ust21510`. `ust31490`(모의 미제공)과 잔고 `ust21070`(아직 쓰지 않음)은 없다.
  - `demo`로 등록되지 않은 키는 생성 단계에서 거부한다. 계좌 참조는 `kiwoom-<sha256(app_key)[:16]>-demo`이고, 요청 본문에 계좌번호가 없다.
  - **지원 시장 기본값은 없음:** 미국 모의 주문 지원이 확인되기 전(P4)에는 `markets`가 비어 있어, 실행기의 한도 검사가 모든 주문을 `market_not_supported`로 막는다.

  - 주문 유형: 지정가 `00`(가격 포함), 시장가 `03`(가격 빈 값).
  - 결과: `return_code` 0이고 주문번호가 있으면 접수, 그 밖의 응답은 거절. 응답을 읽지 못하면(시간 초과, 연결 끊김, 본문 없는 5xx) **미확인**이고 다시 보내지 않는다. 토큰이 다른 클라이언트 발급으로 바뀐 경우(3·8005)만 토큰을 다시 받아 한 번 더 보낸다(처리 전 거절이므로).
  - 조회: 0 채움 숫자, 연속조회(`cont-yn`/`next-key`), 스펙 예시의 `result_lsit` 철자를 함께 읽는다. 모의 미제공 응답(RC9000)은 오류로 올린다.
- **`signals.py`:** 규칙 전략 신호를 백테스트와 같은 `RuleSignals`로 계산한다. 확정 봉만 보여 주고 마지막 확정 봉에서 묻는다. Python 전략, Python 지표 피연산자, 손절·익절(`stop_loss_pct`·`take_profit_pct`)은 아직 거부한다.
- **`runner.py`(`PaperRunner.step`):** 봉 공급원·adapter·시계를 주입받는다.
  1. heartbeat.
  2. 응답 대기·미확인 제출을 당일 주문 목록으로 먼저 맞춘다. 같은 종목·방향·수량·주문유형이면서 다른 제출이 차지하지 않은 주문이 하나면 접수, 없으면 "주문 안 됨"(거절), 둘 이상이거나 이전 증권사 날짜의 제출이면 킬 스위치를 켠다.
  3. 체결 동기화: 잔량 0이고 체결 수량이 있는 접수 주문을 `order_aggregate` 모의 체결 1건으로 저장한다. 체결 시각은 서울 `HH:MM:SS`를 그 시각이 지난 가장 최근 서울 날짜에 놓는다(모의 서버에서 미확인). 수수료는 응답에 없어 `null`이다.
  4. 정지가 아니면 승인 종목마다 마지막 확정 봉을 한 번만 전략에 보인다. 신호 → 수량 계산 → 의도 → 한도 → 신호 나이 → `may_submit` → 주문 유형 확인 → 제출. 제출 기록은 보내기 전에 `pending_response`로 남겨, 도중에 멈추면 다음 주문을 막는다.
  - 수량: 고정 주수, 고정 금액(÷ 기준가 × (1 + 수수료율)), 자산 비율. 자산 비율은 실행 승인에 적은 고정 자산(`equity_basis`)이 있어야 하고 없으면 건너뛴다. 모두 정수 주로 내림. 매도는 모의 원장의 보유 수량 전부.
  - 지정가 진입·청산: 신호 봉 종가 × (1 + `offset_pct`/100)를 $1 이상은 1센트, 미만은 0.0001 단위로 매수는 내림·매도는 올림. 스톱 주문은 보내지 않는다.
  - 신호 나이: 신호 봉 종료 후 `max_signal_age_seconds`(기본 300초)가 지나면 `expired`.
  - 실행 계획(`RunPlan`)의 내용 해시가 승인 ID다. 다른 증권사 계정의 계획은 거부한다.
- **계약 변경:** 결과 미확인(`unknown`) 제출은 응답 시각이 없을 수 있다. 응답 대기에는 응답 시각이 없고, 접수·거절에는 있다.
- **아직 없는 것(P3):** 실제 봉 공급원 연결, 키체인에서 키 읽기, LaunchAgent·`launchctl`, API·화면, 미체결 주문 만료 취소, 일 손실 계산, 환율 출처.

## P3a 구현(2026-10-23, 사용자 승인 "모두 진행")

백엔드 연결이다. 실제 키움 호출은 여전히 없다: 검증된 시장이 기록되지 않으면 모든 주문이 한도 검사에서 막힌다.

- **봉 공급원(`feed.py`, `ServiceBarFeed`):** 차트·백테스트와 같은 bar service를 백테스트 로더(`load_instrument`)로 읽는다. 최근 7일의 정규장을 `now`를 시점 기준(as-of)으로 읽어, 그때 공개되지 않은 봉은 보이지 않는다. 출처·feed·수정주가·리비전이 둘 이상 섞이면 거부한다.
- **상주 실행기(`service.py`):** `uv run python -m services.paper_trading.service [--data-dir] [--interval-seconds 10] [--once]`.
  - 미무장·정지 중에는 heartbeat만 쓴다. 봉을 읽지 않고 증권사도 부르지 않는다.
  - 무장되면 승인 내용으로 계획을 다시 만든다(전략 정의가 승인한 SHA-256과 다르면 거부). 키 저장소에서 계획의 계좌와 맞는 **활성 키움 `demo` 키**만 메모리로 읽는다.
  - adapter의 지원 시장은 `market_verifications` 표에 기록된 시장뿐이다(migration 0002). 기록은 P4에서 사용자 승인 아래 첫 모의 주문을 확인한 뒤에만 한다.
  - 모의 도메인 밖이나 허용목록 밖으로 나가려는 요청이 생기면 킬 스위치를 켠다. 그 밖의 오류는 기록하고 다음 회차에 다시 시도한다.
- **API(`services/api/paper_routes.py`):** 주문 엔드포인트는 없다.
  - 읽기: `GET /v1/paper/status`, `/v1/paper/approvals`, `/v1/paper/intents?limit=`, `/v1/paper/executions?limit=`.
  - 시작 쪽(`POST /v1/paper/approvals`, `/arm`, `/release`)은 Tauri 출처(`tauri://localhost`)만 받고, 다른 출처는 403이다.
  - 멈추는 쪽(`POST /v1/paper/kill`, `/disarm`)은 어느 호출자든 받는다. 멈추는 것은 언제나 안전하기 때문이다.
  - 승인 요청: 전략 ID·버전, 종목(키움 거래소 코드가 있는 미국 상장만), 키움 `demo` 키의 credential ID, 한도(1건 기본 100만 원, 나머지 기본 없음), 시장가 버퍼(기본 50bp), 수수료율, 환율(사용자가 입력, 출처와 승인 시각 기록), 자산 비율용 고정 자산, 신호 최대 나이. 실행기가 돌릴 수 없는 전략(Python, 손절·익절)은 승인 단계에서 거부한다. 계좌 참조는 앱 키 해시이며 키 값은 응답에 없다.
- **계약:** `paper_approval`, `paper_approval_list_response`, `paper_intent_list_response`, `paper_execution_list_response`.
- **환율 출처(결정):** 실행 승인 때 사용자가 입력한 고정 환율을 쓴다. 출처 문구와 승인 시각을 의도에 남긴다. 키움 `exch_rate`는 실제 응답을 확인하지 않아 쓰지 않는다.
- **아직 없는 것(P3b):** Tauri 본체의 API 기동·LaunchAgent 설치·`launchctl` 정지, `dist-agent`/`dist-research` 빌드 분리, Agent 화면.

## Alternatives

- **KIS만 기다린다:** 사용자가 지금 KIS API를 등록할 수 없어 단계 1을 시작할 수 없다.
- **키움 전용으로 설계한다:** 먼저 끝나지만 KIS를 붙일 때 원장·의도 계약을 다시 고쳐야 한다. 증권사 중립 계약에 adapter를 두는 비용이 작다.
- **API 프로세스 안에서 주문 루프를 돌린다:** 구조는 단순하지만 API 재시작·오류가 주문 루프와 함께 움직인다. Research 앱도 같은 API를 쓰므로 주문 경로가 공유된다.
- **앱이 열려 있을 때만 실행:** 통제는 쉽지만 앱을 끄면 전략이 멈춘다. 사용자가 상주를 골랐다.
- **실행 중 셸 감지로 화면 분기:** 빌드는 하나로 끝나지만 Research 번들에 주문 화면 코드가 남는다.
- **모의 체결을 `broker_api` 원장에 `environment: demo`로 넣는다:** 표는 줄지만 한 필터만 빠져도 실제 체결과 섞인다. 도메인 규칙(실제/모의 분리)에 어긋난다.
- **지정가만 허용:** 주문 금액 검사가 정확하지만, 사용자가 시장가도 허용하기로 했다. 시장가는 추정 상한가로 검사한다.
- **미체결 일괄 취소 킬 스위치:** 사용자가 신규 주문만 중지하기로 했다.

## Consequences

- 저장소가 하나(`paper_orders.sqlite3`), 서비스 패키지가 하나(`services/paper_trading`), 계약이 넷 늘어난다.
- Tauri 본체에 LaunchAgent 설치·`launchctl` 관리 코드가 생긴다. 지금의 `lib.rs`는 창만 연다.
- 실행기가 앱 밖에서 상주하므로, 사용자가 앱을 열지 않아도 모의 주문이 나갈 수 있다. 화면을 열면 마지막 heartbeat와 그동안의 주문을 먼저 보여 준다.
- 일 주문 수·일 손실 한도가 없으므로, 전략 오류가 있으면 1건 100만 원 이하 주문이 계속 나갈 수 있다. 모의투자라 실제 손실은 없지만, 한도를 넣기 전에는 킬 스위치와 화면 확인이 유일한 제동이다.
- 화면 빌드가 둘이 된다. CI의 빌드 시간이 늘고 Electron 패키징 경로가 바뀐다.
- 모의 체결은 증권사 모의 서버의 시뮬레이션이다. 실거래 체결 품질(슬리피지·부분 체결)을 대표하지 않는다. 화면과 단계 2 검토 자료에 그렇게 적는다.
- 키움의 실전·모의 구분은 도메인뿐이므로 host 검사 테스트가 이 설계에서 가장 중요한 테스트다.

## 남은 결정

- **P0 결론:** 키움 모의에 미국 계좌가 있고 잔고 조회(`ust21070`)가 된다. 주문 가능 수량 조회(`ust31490`)는 모의에서 제공되지 않는다. 미국 주문의 모의 지원은 P4에서 확인한다. 대안 (a)~(c)는 P4에서 미국 주문이 거절될 때 사용자가 고른다(9절).

- **나중에 적용할 한도 값:** 일 주문 수, 일 손실률, 종목별 보유.
- **KIS:** 11월 중순 등록 예정(사용자). 등록 뒤 P5를 시작한다.
