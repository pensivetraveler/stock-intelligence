# ADR 0058 — Pine 지표를 가져올 때 자체 지표로 변환

- **Status:** accepted. 2026-11-15 사용자가 방향을 정하고("Pine은 입력 통로") 이 ADR을 승인했다("승인"). 같은 승인으로 구현 1단계를 시작한다. 2~4단계는 단계마다 사용자 승인 뒤에 구현한다.
- **Date:** 2026-11-15
- **Related:** [ADR 0026](0026-formula-indicators.md)(수식 지표), [ADR 0040](0040-pine-script-indicators.md)(Pine 해석기), [ADR 0042](0042-claude-assistants.md)(Pine 전략 → 규칙 변환, 지표 도우미), [ADR 0023](0023-python-custom-indicators.md)(Python 지표)

## Context

### 측정(2026-11-15, `perf/pine-long-charts`)

`apps/desktop/src/pine.perf.test.ts`(`SIW_PINE_PERF=1`일 때만 실행)로 합성 1분봉에서 `runPine` 한 번의 시간을 쟀다. i9-9900K, Node 22, 5번 실행의 중앙값이다. 다른 프로세스가 돌던 중이라 같은 조건에서도 2배 가까이 흔들렸다.

| 스크립트                 | 1,200봉 | 5,000봉 | 13,200봉 | 50,000봉       |
| ------------------------ | ------- | ------- | -------- | -------------- |
| EMA 교차(`PINE_EXAMPLE`) | 16ms    | 65ms    | 155ms    | 0.84초         |
| strategy 예제            | 70ms    | 283ms   | 577ms    | 2.4초          |
| `ta.*` 7개와 `plotshape` | 85ms    | 413ms   | 749ms    | 3.5초          |
| 봉마다 50번 반복         | 130ms   | 362ms   | 1.7초    | 반복 한도 오류 |
| 배열 이동 창(100)        | 38ms    | 155ms   | 318ms    | 1.2초          |
| 선·라벨 그리기           | 33ms    | 90ms    | 194ms    | 0.65초         |
| 내장 EMA 2개 + RSI       | 1ms     | 2ms     | 6ms      | 32ms           |

같은 식(`(ema12 − ema26) / atr14 + rsi14 − sma20`)을 13,200봉에서 계산하면 수식 지표는 약 24ms, Pine은 약 210~360ms였다.

- 1,200봉은 차트의 기본(`DEFAULT_CANDLES`)이고, 13,200봉은 이전 봉을 끝까지 불러온 경우(`DEFAULT_CANDLES` + `MAX_OLDER_BARS`)다.
- CPU 프로파일을 보면 시간이 해석기 본체에 고르게 퍼져 있다. 인자 평가 19%, 문장 실행 15%, 호출 14%, 식 평가 12%, 가비지 컬렉션 12%였다. 함수 하나를 고쳐서 풀 문제가 아니다.
- 지표는 `ChartPanel.tsx`의 `useMemo`에서 메인 스레드로 계산되고, 봉 배열이 바뀌면 처음부터 다시 계산한다. 리플레이는 한 칸마다 봉 배열이 바뀐다. 그래서 긴 차트에서는 한 칸마다 화면이 0.2~1.7초 멈출 수 있다. 실시간 시세가 같은 경로로 다시 계산하는지는 확인하지 않았다.
- 반복 한도(`MAX_LOOP_STEPS` 2,000,000)는 실행 전체에 걸린다. 그래서 정상 스크립트도 차트가 길면 실패한다. TradingView의 한도는 봉 하나 기준이다.
- 차트 라이브러리(`lightweight-charts`)는 그리기만 한다. 위 시간에는 들어 있지 않다. 그리기 시간은 재지 않았다.

### 사용자 결정(2026-11-15)

> "pinescript는 tradingview의 스크립트를 빠르게 받아들여서 우리의 지표로 소화하기 위한 인풋 채널 역할이야. 지표를 반드시 pinescript로 만들 필요는 없어."

그러니 Pine 해석기를 빠르게 만드는 것보다, 가져올 때 자체 지표로 바꾸는 게 목적에 맞다. 차트를 직접 만드는 안도 사용자가 꺼냈다. 하지만 측정상 느린 쪽은 해석기이므로 이번 범위에 넣지 않는다(아래 "고려한 대안").

## Decision

### 1. 가져올 때 바꾼다

Pine 지표를 추가할 때(보조지표 창의 Pine 편집기, 지표 도우미의 결과, TradingView 코드 붙여넣기) 스크립트로 변환을 시도한다.

1. **변환됨:** 수식 지표(`type: "formula"`)로 저장하고 차트에서는 수식으로 계산한다.
2. **변환 안 됨:** 지금처럼 `type: "pine"`으로 저장하고 해석기로 계산한다. 설정 창에 막힌 이유(줄·칸과 기능 이름)와 "긴 차트에서 느릴 수 있음"을 보인다.

변환은 LLM 없이 코드로 한다. Pine 구문 트리(`pine-parser.ts`)를 수식 트리로 옮긴다. 결과가 정해져 있어 같은 입력이면 같은 결과가 나오고, 모델 배정이 필요 없다. 변환 못 한 스크립트를 LLM으로 다시 쓰는 일은 이 ADR에 넣지 않는다. 하게 되면 그때 모델 배정을 상담한다(AGENTS.md).

### 2. 수식 언어를 넓힌다(ADR 0026 개정)

ADR 0026의 "Revisit when"에 적힌 "조건·여러 출력"을 이번에 연다. 기존 수식은 그대로 유효하다.

- **비교·논리·선택:** `> < >= <= == !=`, `and or not`, `cond ? a : b`. 참/거짓은 1/0이 아니라 별도 값으로 다룬다. 결측 규칙은 Pine을 따른다(결측과 비교하면 거짓).
- **이전 값:** `x[n]`(n은 상수 0~500)을 `shift(x, n)`과 같게 받는다.
- **설정값:** Pine `input.int/float/bool/source`는 지표 설정값이 된다. 길이 인자에는 상수와 함께 설정값을 쓸 수 있다(범위 1~500은 그대로). 워밍업 길이는 설정값을 대입해 계산한다.
- **여러 출력:** 이름이 붙은 식 여러 개가 각각 `plot` 하나가 된다. 출력마다 표시 이름, 색(상수 또는 `cond ? 색 : 색`), 두께, 선·히스토그램을 가진다. `hline`은 기준선(`levels`)이 된다.
- **함수 추가:** Pine `ta.*` 중 인과성이 테스트된 차트 내장 공식에 대응하는 것만 넣는다. 첫 묶음은 `crossover`·`crossunder`, `cum`, `macd`·`bb`(튜플은 출력별 함수로 나눔), `stoch`, `cci`, `mfi`, `tr`, `nz`다. 정확한 목록은 구현 때 내장 공식과 대조해 정한다.
- **안전:** 지금처럼 직접 만든 파서와 트리 순회로만 계산한다. `eval`과 `new Function`은 쓰지 않는다. 길이 한도(500자·200노드)는 여러 출력의 합으로 다시 정한다.

### 3. 첫 단계에서 바꾸는 Pine

다음만 쓰는 스크립트를 변환한다.

- `indicator()`, `input.*`, 맨 위 단계의 선언(`x = …`)과 튜플 선언(`[a, b] = ta.macd(…)`)
- 산술·비교·논리·삼항 연산, 상수 n의 `x[n]`, 위 함수 목록
- `plot`(색은 상수 또는 삼항), `hline`

나머지는 변환하지 않는다. `var`, `:=`, 반복문, `if` 블록, 사용자 함수, 배열, 그리기 객체, `plotshape`·`bgcolor`·`fill`, `request.*`, `strategy`, `barstate.*`·`time` 계열이 여기에 든다. 사용자 함수 펼치기, `if` 블록을 삼항으로 바꾸기, `plotshape` 같은 그래픽은 실제 스크립트에서 얼마나 막히는지 보고 다음 단계로 정한다.

### 4. 같은지 확인하고 나서 "변환됨"으로 둔다

변환 결과를 저장하기 전에 Pine 해석기와 수식으로 같은 봉을 계산해 출력별로 모든 봉을 비교한다.

- **봉:** 추가하는 차트의 봉과 고정 표본 봉(급변·결측·0 거래량 포함)을 쓴다.
- **판정:** 값은 상대 오차 1e-9 안이어야 하고, 결측 위치는 같아야 한다. 하나라도 다르면 Pine으로 남기고 다른 첫 봉과 출력을 기록한다.
- **범위:** "이 봉들에서 같았다"는 뜻이지 두 프로그램이 같다는 증명이 아니다. 화면과 기록에 그렇게 적는다.

### 5. 출처를 남긴다

변환된 수식 지표에 원래 Pine 코드, 그 SHA-256, 변환기 버전, 비교한 봉 수를 함께 저장한다(AGENTS.md: 지표 버전과 근거 기록). 설정 창에서 원본을 볼 수 있다. 수식을 고치면 "Pine에서 변환됨" 표시를 "변환 후 수정됨"으로 바꾼다.

### 6. 해석기는 남기고 한도만 고친다

해석기는 변환 안 되는 스크립트의 대체 경로이자 비교 기준으로 남긴다.

- 반복 한도를 봉 하나 기준으로 바꾼다(값은 구현 때 측정해 정한다).
- 해석기 최적화와 Worker 이동은 하지 않는다. 아래 "다시 볼 조건"에 해당할 때 다시 본다.

### 구현 순서(단계마다 사용자 승인)

1. 반복 한도를 봉 하나 기준으로 바꾸고, 측정 파일을 저장소에 넣는다.
2. 수식 언어를 넓힌다(§2). 파서, 계산, 워밍업, 편집기, 인과성 테스트가 들어간다.
3. 변환기와 비교(§3·§4), 저장과 출처(§5), 화면 표시를 만든다.
4. 사용자가 실제로 쓰는 TradingView 스크립트로 변환율을 재고, 막힌 기능 순위를 낸다.

## 고려한 대안

- **해석기 최적화(분기·키·스코프를 미리 정하기):** 2~5배쯤 빨라질 것으로 보지만 측정하지 않았다. 빨라져도 봉 하나마다 코드 전체를 해석하는 구조는 같아서 수식보다 느리다. 또 Pine을 자체 지표로 소화한다는 목적과 어긋난다.
- **Worker로 옮기기:** 화면은 멈추지 않지만 계산 시간은 그대로다. 지표가 늦게 따라오는 처리(이전 값 유지, 오래된 계산 버리기)도 필요하다. 변환 안 된 스크립트가 많이 남으면 다시 본다.
- **새 봉만 이어서 계산:** 리플레이·실시간에서 가장 빠르지만, 해석기 상태를 저장하고 되살려야 해서 가장 크다.
- **Pine을 JavaScript로 컴파일:** 빠르지만 생성 코드를 실행해야 해서 ADR 0040의 "eval 없음"과 충돌한다.
- **Python 지표로 변환:** API 왕복이 생기고, 차트에서는 수식보다 느리다. 백테스트 연결은 쉬워진다.
- **차트 직접 제작:** 측정상 느린 곳은 그리기가 아니라 해석기다. 이번 문제를 풀지 못한다. 그리기가 느리다는 측정이 나오거나 라이브러리로 할 수 없는 기능이 생기면 다시 본다.

## 결과와 대가

- 변환된 지표는 내장 지표에 가까운 속도로 계산된다(13,200봉에서 수십 ms 예상).
- 수식 언어가 커진다. 문법, 결측, 참/거짓 규칙을 문서와 편집기 도움말에 적어야 한다.
- 변환된 지표를 고칠 때는 Pine이 아니라 수식을 고친다. Pine으로 고치고 싶으면 원본을 고쳐 다시 가져온다.
- 수식은 아직 백테스트에서 쓸 수 없다(ADR 0026). 변환됐다고 백테스트에 바로 쓸 수 있는 것은 아니다. 백테스트 연결에는 Python 수식 계산기와 공용 일치 fixture가 필요하고, 별도 단계로 둔다.
- 저장된 `type: "pine"` 지표는 그대로 둔다. 일괄 변환은 미리보기와 되돌리기가 가능할 때만 사용자가 실행한다(AGENTS.md 프리셋 규칙과 같은 원칙).

## 다시 볼 조건

- 실제 스크립트의 변환율이 절반에 못 미친다. 그러면 해석기 최적화나 Worker를 다시 본다.
- 변환됐는데 다른 봉에서 Pine과 값이 다른 사례가 1건이라도 나온다. 그 기능의 변환을 즉시 막고 원인을 본다.
- 변환 안 된 지표 때문에 긴 차트에서 화면이 멈춘다는 보고가 나온다.
- 차트 그리기 시간이 지표 계산보다 커진다는 측정이 나온다.
