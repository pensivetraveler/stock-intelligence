# ADR 0037 — SIW Agent 단계 1: 한국투자(KIS) 모의투자 주문 실행 설계

- **Status:** proposed (설계만. 구현은 사용자의 별도 명시 승인이 있어야 시작한다)
- **Date:** 2026-10-23
- **Related:** [ADR 0036](0036-desktop-app-roles.md)(앱 역할·주문 Gate), [ADR 0018](0018-broker-api-execution-ledger.md)(증권사 API 원장), [ADR 0021](0021-backtest-engine.md)(백테스트 엔진·전략 버전), [ADR 0013](0013-broker-market-data-adapters.md)·[ADR 0014](0014-provider-key-registry.md)(KIS 시세 연동·키 보관), [ADR 0028](0028-electron-desktop-shell.md)(Electron의 API 기동)

## Context

ADR 0036은 Tauri 앱 **SIW Agent**가 승인된 전략을 실행하고, 주문은 단계별 Gate로 넓힌다고 정했다. 단계 1은 한국투자(KIS) 모의투자 주문만이고, 이 ADR은 그 설계다.

현재 코드에서 확인한 사실:

- **KIS 연동은 시세 조회 전용이다.** `services/market_data/kis.py`는 해외주식 분봉만 읽는다. `AllowlistedClient`가 토큰 발급(POST)과 분봉 조회(GET) 두 경로만 허용한다.
- **모의투자 도메인은 이미 있다.** `DEMO_BASE_URL = "https://openapivts.koreainvestment.com:29443"`(공식 open-trading-api `kis_devlp.yaml`의 `vps`). 키 등록 화면에서 계좌 환경을 `demo`로 등록하면 시세 조회가 이 도메인으로 간다(`account_environment`). 환경은 등록한 키에서만 오고 프로세스 환경변수로 바꿀 수 없다.
- **키는 OS 키체인에 있다.** KIS 키는 `app_key`·`app_secret` 두 칸이다(`services/credentials/catalog.py`). 주문에 필요한 계좌번호 칸은 아직 없다.
- **원장은 넷이다.** 수동 실제 체결, 거래내역서 가져오기, 증권사 API(`broker_api`, ADR 0018), 가상 시나리오는 저널 저장소에 있다. 백테스트 체결은 `backtests.sqlite3`에만 있다(ADR 0021).
- **전략은 불변 버전이다.** 버전마다 정의와 SHA-256이 있다. Python 전략은 격리 프로세스에서 봉 하나씩 받는다(ADR 0021).
- **Tauri 앱은 API를 띄우지 않는다.** `src-tauri/src/lib.rs`는 창만 연다. Electron은 저장소를 찾아 `uv run uvicorn`을 띄운다(ADR 0028).
- **두 앱은 같은 화면 빌드(`apps/desktop/dist`)를 쓴다.**

KIS 공식 문서 기준이고 **실계정으로 확인하지 않은 것**(`unverified`):

- 모의투자는 실전과 다른 앱 키·계좌를 쓴다.
- 주문 TR ID가 실전 `T…`, 모의 `V…`로 갈린다. 예: 국내 현금주문 `TTTC0012U` ↔ `VTTC0012U`.
- 모의투자의 호출 한도는 실전보다 낮다.
- 모의 체결은 KIS 모의 서버가 만든 체결이고, 시장에서 실제로 체결된 것이 아니다.

## Decision (제안)

### 1. 모의 주문 원장: 기존 원장과 분리

- **저장소:** `SIW_DATA_DIR/paper_orders.sqlite3`. 저널(`journal.sqlite3`)과 백테스트 저장소에 넣지 않는다. 번호 기반 migration을 쓴다.
- **원장 유형:** `kis_paper`(모의 증권사 체결). 기존 4개 원장 유형과 백테스트 체결 중 어느 것과도 합산하지 않는다.
  - 대사(ADR 0025), 매매 복기 Agent의 실제 체결(ADR 0022), 브로커 원장 포지션 계산은 이 원장을 읽지 않는다. 테스트로 확인한다.
  - 차트에 그릴 때는 백테스트 `BT`처럼 별도 마커(예: `PAPER`)와 "모의 체결" 칩을 쓴다. 실제 체결 마커와 같은 모양으로 그리지 않는다.
- **표(초안):**
  - `order_intents`: 주문 의도(2절). 추가만 하고 고치지 않는다.
  - `order_submissions`: 의도 1건에 제출 시도 1건. 요청 시각, 응답 시각, KIS 주문번호, 응답 코드·메시지(200자 이내), 상태(`pending_response → accepted | rejected | unknown`).
  - `paper_executions`: KIS 모의 체결 조회로 받은 체결.
    - 조회 응답이 주는 단위 그대로 저장한다. 건별 체결이 아니면 ADR 0018처럼 `granularity: order_aggregate`로 표시한다.
    - 시각의 의미(`time_meaning`)를 기록하고, 응답에 없는 체결 순서나 시각을 만들지 않는다.
    - `fill_origin: broker_demo_simulated`로 시장 체결이 아님을 표시한다.
  - `limit_events`·`kill_switch_events`: 한도 거절, 킬 스위치 켜기·끄기, 재무장(arm) 기록.
- **금액·수량:** Decimal 문자열. 통화(KRW/USD)는 원장 행마다 둔다.
- **계약(신규, JSON Schema 2020-12):** `paper_order_intent`, `paper_order_submission`, `paper_execution`, `paper_runner_status`. Python·TypeScript validator, fixture, 생성 타입을 같은 작업에서 추가한다.

### 2. 주문 의도(order intent) 계약

전략 신호가 주문이 되기 전에 반드시 의도 1건을 기록한다. 기록하지 못하면 주문하지 않는다.

- **식별:**
  - `intent_id`: `sha256(strategy_id, strategy_version, instrument_id, side, signal_bar_start_utc)`에서 만든다. 같은 신호는 재시작 뒤에도 같은 ID라서 두 번 제출되지 않는다.
  - `created_at_utc`.
- **전략:**
  - `strategy_id`, `strategy_version`, `definition_sha256`.
  - `approval_id`: 3절의 실행 승인 기록.
  - `strategy_kind`(`rules`/`python`). Python이면 샌드박스 출력 `logs`의 해시도 둔다.
- **데이터 시점(cutoff):**
  - `data_as_of_utc`: 판단에 쓴 데이터의 기준 시각.
  - `signal_bar_start_utc`/`signal_bar_end_utc`, 그리고 `signal_bar_final: true`. 확정되지 않은 봉이면 의도를 만들지 않는다.
  - 봉 출처 묶음: `source_id`, `feed_scope`, `dataset_revision`, `adjustment`, 세션, 입력 봉 개수와 SHA-256(ADR 0021 입력 고정과 같은 방식).
  - 거래소 현지시간과 캘린더 ID·버전.
- **신호 근거:**
  - 규칙 전략: 평가한 조건 트리와 각 피연산자 값(지표 ID·파라미터·출력·값).
  - Python 전략: `ctx.buy/sell` 호출 내용과 그 봉의 지표 값.
  - 근거는 값과 출처만 담는다. 해설(Agent 추론)은 따로 두고 섞지 않는다.
- **수량·가격 계산:**
  - `sizing_method`(`shares`/`cash`/`percent_equity`)와 입력값.
  - 계산에 쓴 기준 자산·현금(모의 원장 기준, 시각 포함), 기준 가격과 그 출처(예: 신호 봉 종가), 수수료 가정, 내림 규칙.
  - 결과 `quantity`.
  - `order_type`: 단계 1은 지정가 `limit`만 제안한다(시장가는 아래 미결 질문). 지정가와 그 계산식(예: 기준가 × (1 + 허용 bp), 호가 단위 내림)을 남긴다.
- **한도 검사 결과:** 검사한 한도 값과 통과·거절 사유(4절).
- **상태:** `recorded → submitted | blocked(사유) | expired`.
  - 신호 봉 다음 거래 세션 안에 제출하지 못하면 `expired`로 두고 나중에 몰아서 제출하지 않는다.

**백테스트와의 차이:** 백테스트는 다음 봉 시가에 체결된다고 가정한다(ADR 0021). 모의 주문은 신호 봉이 확정된 뒤 제출하므로 체결가가 다르다. 의도에 기준 가격을 남겨, 화면에서 "백테스트 가정가 대비 모의 체결가" 차이를 보여 준다. 이것은 참고 지표이고 실거래 성과를 보장하지 않는다.

### 3. 전략 입력과 실행 승인

- SIW Agent는 Research에서 저장한 전략 버전만 실행한다. 실행 단위는 `strategy_id@version` + `definition_sha256`으로 고정한다.
- **실행 승인 기록(`approval_id`):** 사용자가 SIW Agent 화면에서 버전, 대상 종목, 한도, 계좌 참조를 보고 승인한다. 승인 시각과 내용 해시를 저장한다. 다음 경우에는 새 승인이 필요하다.
  - 전략 버전, 종목, 한도 중 하나라도 바뀐다.
  - Agent가 만든 전략 코드다(기존 규칙). 이때는 코드 검토 승인이 먼저 있어야 한다.
- Python 전략은 백테스트와 같은 샌드박스(빈 환경변수, 네트워크 차단 감사 훅, 봉 하나씩 전달)에서 돈다. 전략 코드는 키·토큰·주문 클라이언트에 닿지 않는다. 전략은 의도만 돌려주고, 제출은 실행기가 한다.

### 4. 실계좌 도메인 차단(코드)

실계좌 주문은 단계 2 승인 전까지 호출할 수도 시험할 수도 없게 만든다. 설정으로 열 수 있는 길을 두지 않는다.

- **별도 모듈:** `services/paper_trading/kis_paper_client.py`. 시세 모듈 `kis.py`의 `KisConfig.base_url`·`SIW_KIS_BASE_URL`을 재사용하지 않는다.
- **도메인 상수 고정:** 주문 클라이언트의 기본 URL은 모듈 상수 `DEMO_BASE_URL` 하나다. 생성자에 URL 인자가 없다(테스트는 `transport`만 바꾼다).
- **요청마다 검사:** 요청 직전에 실제 요청 URL의 scheme·host·port가 `openapivts.koreainvestment.com:29443`인지 확인한다. 아니면 `LiveDomainBlockedError`를 던지고 아무것도 보내지 않는다.
- **TR ID 검사:** 주문·정정·취소·체결 조회 TR ID는 허용목록 상수로 둔다. 모두 `V`로 시작해야 하고, `T`로 시작하는 TR ID는 거부한다.
- **허용목록:** `AllowlistedClient`와 같은 방식으로 (method, path)를 제한한다. 단계 1의 경로는 다음뿐이다.
  - 토큰 발급, 해시키(문서상 필요하면), 주문, 취소.
  - 주문·체결 조회, 잔고 조회.
  - 정정은 필요할 때 따로 추가한다.
- **키 환경 검사:** 키 등록에서 환경이 `demo`인 KIS 키만 주문 클라이언트에 넘긴다. `real` 키를 넘기면 생성 단계에서 거부한다.
- **정적 검사:** `verify.sh`에 검사를 추가한다. 주문 모듈 디렉터리에 실전 도메인 문자열(`openapi.koreainvestment.com:9443`)이나 `T`로 시작하는 주문 TR ID가 나타나면 실패한다.

### 5. 한도와 킬 스위치

**한도:** 실행 승인에 포함되는 값이다. 제출 직전에 코드에서 검사하고, HTTP 요청보다 먼저 한다.

| 한도        | 내용                                                                                    |
| ----------- | --------------------------------------------------------------------------------------- |
| 종목        | 승인한 종목 허용목록만. 목록 밖 의도는 `blocked: symbol_not_allowed`                    |
| 주문 금액   | 1건의 수량 × 지정가 상한(통화별)                                                        |
| 종목별 보유 | 종목당 최대 보유 금액·수량                                                              |
| 일 주문 수  | 거래소 현지 날짜 기준 제출 건수 상한(거절·취소 포함)                                    |
| 일 손실     | 당일 시작 모의 평가액 대비 손실 상한. 넘으면 킬 스위치를 자동으로 켠다                  |
| 호출 간격   | 모의 호출 한도(문서상 값, 미검증)보다 보수적인 최소 간격                                |
| 미확인 주문 | 응답이 없는(`unknown`) 제출이 1건이라도 있으면 새 주문 금지. 조회로 상태를 맞춘 뒤 재개 |

- **한도 변경:** 한도를 조이면 즉시 적용한다. 늘리면 새 실행 승인이 필요하다.
- **보수적 기본값:** 평가 가격을 구할 수 없거나 모의 잔고 조회가 실패해 일 손실을 계산할 수 없으면 주문하지 않는다.

**킬 스위치:**

- **켜는 방법:**
  - SIW Agent 화면 상단의 항상 보이는 버튼.
  - 메뉴와 단축키.
  - 일 손실 한도 도달 시 자동.
  - 이상 상태(미확인 주문이 일정 시간 넘게 지속, 데이터 출처·리비전 불일치, 시계 차이) 시 자동.
- **동작:**
  1. `paper_orders.sqlite3`에 정지 상태를 기록한다. 실행기는 제출 직전에 이 상태를 다시 읽는다.
  2. Tauri 본체(Rust)가 실행기 프로세스를 종료한다. API나 화면이 응답하지 않아도 Rust 쪽만으로 멈출 수 있다.
  3. 선택: 미체결 모의 주문 취소. 취소도 모의 도메인으로만 간다. 기본은 "신규 중지만"이고 일괄 취소는 사용자가 고른다(미결 질문).
- **해제:** 정지 해제만으로는 다시 주문하지 않는다. 사용자가 재무장(arm)해야 하고, 그 기록이 남는다.
- **앱 종료:** SIW Agent를 끄면 실행기도 멈춘다. 꺼진 동안 주문은 없다.

### 6. 실행 구조: API와 상주 실행기

**제안:** 실행기는 API와 분리한 프로세스로 둔다. Tauri 본체가 두 프로세스의 생명주기를 관리한다.

```
SIW Agent (Tauri, Rust)
 ├─ 화면 (agent 빌드)  ── HTTP ──▶  API (uvicorn, 127.0.0.1:8765)  ── 읽기: 모의 원장·상태 / 쓰기: 승인·킬 스위치
 └─ 실행기 프로세스 (python -m services.paper_trading.runner)
       ├─ 봉 조회 (기존 bar service, 확정 봉만)
       ├─ 전략 평가 (기존 샌드박스)
       ├─ 의도 기록 → 한도 검사 → KIS 모의 주문 클라이언트
       └─ paper_orders.sqlite3 (단일 쓰기 주체)
```

- **API 기동:** Electron과 같은 규칙을 Rust로 옮긴다(ADR 0028).
  - 127.0.0.1:8765가 이미 응답하면 그 API를 쓴다.
  - 아니면 `SIW_REPO_DIR` → 앱 설정에 저장한 폴더 → 폴더 선택 순으로 저장소를 찾고 `uv run uvicorn`을 띄운다.
  - 자기가 띄운 API만 종료 시 멈춘다. 로그는 `~/Library/Logs/siw-agent/`.
- **실행기 기동:** 사용자가 화면에서 실행 승인한 뒤 "시작"을 눌렀을 때만 Rust가 띄운다.
  - Tauri 앱이 열려 있는 동안만 돈다. 앱 밖 상주(launchd 등)는 단계 1에 넣지 않는다.
  - 실행기는 `SIW_DATA_DIR`가 없거나 KIS 모의 키가 없으면 시작하지 않는다.
- **분리 이유:**
  - 화면이나 API의 오류·재시작이 주문 루프를 건드리지 않는다.
  - 주문 클라이언트와 키 읽기는 실행기 안에만 있다. API에는 주문 엔드포인트가 없다.
  - Rust가 프로세스를 직접 종료할 수 있어 킬 스위치가 API에 의존하지 않는다.
- **API의 모의 주문 관련 엔드포인트(초안):**
  - 읽기: `GET /v1/paper/status`, `GET /v1/paper/intents`, `GET /v1/paper/executions`.
  - 쓰기: `POST /v1/paper/approvals`, `POST /v1/paper/kill`, `POST /v1/paper/arm`.
  - 쓰기 엔드포인트는 Tauri 출처(`tauri://localhost`)만 받는다. Electron 출처 `siw://app`과 개발 서버 출처는 403이다. 출처 헤더는 로컬 프로세스가 꾸밀 수 있으므로 웹 페이지와 Research 앱을 막는 장치로만 본다. 실제 주문 권한은 실행기에만 있다.
- **재시작 복구:** 실행기는 시작 때 `pending_response`·`unknown` 제출을 KIS 모의 주문 조회로 먼저 맞춘다. 끝나기 전에는 새 주문을 내지 않는다.
- **시각:** 판단과 기록은 UTC로 한다. 세션 판단은 거래소 캘린더로 한다. 로컬 시계와 KIS 응답 시각이 크게 어긋나면 자동 정지한다.

### 7. 화면: SIW Agent와 SIW Research의 차이

**제안:** 빌드를 분리한다. 같은 소스에서 `VITE_SIW_APP=agent|research`로 두 번 빌드하고, Tauri는 `dist-agent`, Electron은 `dist-research`를 싣는다. 실행 중 셸을 감지하는 방식보다 낫다. Research 빌드에는 모의 주문 화면 코드가 아예 들어가지 않기 때문이다.

|         | SIW Agent                                                                            | SIW Research                  |
| ------- | ------------------------------------------------------------------------------------ | ----------------------------- |
| 첫 화면 | 실행 상태판: 실행기 상태, 무장 여부, 킬 스위치(항상 보임), 오늘 주문 수·손익 대 한도 | 지금의 차트 워크스페이스      |
| 전략    | 승인된 버전 목록, 실행 승인 화면(버전·종목·한도·계좌 참조 확인)                      | 작성·수정·백테스트·워크포워드 |
| 주문    | 의도 목록(근거·데이터 시점·계산 펼침), 제출·거절·체결, 백테스트 가정가 대비 차이     | 없음                          |
| 차트    | 실행 종목 차트 + `PAPER` 마커(읽기 위주)                                             | 전체 기능                     |
| 표시    | 상단 띠 "모의투자 — 실제 주문 아님"과 계좌 참조(끝 4자리)                            | 주문 기능 없음 표시           |

Research에서 승인된 전략 버전을 "Agent에서 실행"으로 넘기는 연결은 단계 1에 두지 않는다. Agent에서 버전을 직접 고른다.

### 8. 키와 계좌번호

- 이번 설계 작업에서는 키·계좌번호를 다루지 않았다.
- 구현 때 KIS 키 항목에 모의 주문용 계좌번호(종합계좌 8자리 + 상품코드 2자리, 문서 기준) 칸을 비밀 값으로 추가하고, 키체인에 저장한다.
- 원장·로그·화면에는 `kis-<sha256(app_key)[:16]>-demo` 같은 참조와 끝 4자리만 남긴다(ADR 0018과 같은 방식).
- 키 등록은 사용자가 Keys 화면에서 직접 한다.

### 9. 구현 단위(각각 사용자 승인 후 착수)

1. **P1:** 계약·`paper_orders.sqlite3`·의도 기록·한도 검사·킬 스위치 상태. 외부 호출 없음.
2. **P2:** 모의 주문 클라이언트와 실행기. 로컬 가짜 KIS 서버(`httpx.MockTransport`)로만 시험한다.
3. **P3:** Tauri 본체의 API·실행기 기동, 킬 스위치, `dist-agent`/`dist-research` 빌드 분리와 Agent 화면.
4. **P4:** 첫 실제 모의 도메인 호출. 사용자가 모의 키·계좌를 등록하고 명시적으로 승인한 뒤에만 한다. 종목 1개, 최소 수량, 지정가로 시작한다.

## Test plan

**자동 테스트(P1~P3, 외부 호출 없음):**

- **실계좌 차단:**
  - 주문 클라이언트에 URL을 넘길 방법이 없다(생성자 시그니처 테스트).
  - `transport`를 바꿔 실전 host로 향하게 해도 `LiveDomainBlockedError`가 나고 요청이 0건이다.
  - `T…` TR ID와 허용목록 밖 경로를 거부한다.
  - `real` 환경 키를 거부한다.
  - `verify.sh` 정적 검사가 실전 도메인 문자열을 넣은 임시 파일에서 실패한다.
- **원장 분리:**
  - 모의 주문·체결 뒤 저널 파일 바이트가 그대로다.
  - 대사·매매 복기·브로커 포지션 결과가 바뀌지 않는다.
  - 백테스트 저장소에 모의 행이 없다.
- **의도 계약:**
  - 스키마 valid/invalid fixture. Python·TypeScript validator가 같은 결과를 낸다.
  - 의도 없이는 제출 함수가 호출되지 않는다.
  - 같은 신호를 다시 처리하면 `intent_id`가 같고 제출은 1건이다.
- **미래 데이터 차단:**
  - 확정되지 않은 봉은 의도를 만들지 않는다.
  - `data_as_of_utc` 이후 봉을 데이터 소스에 넣어도 신호가 바뀌지 않는다.
  - 봉 출처·리비전이 섞이면 거부한다.
- **수량·가격:** Decimal 계산, 내림, 호가 단위, 현금 부족, 수량 0을 시험한다. 같은 입력에서 의도 바이트가 같다.
- **한도:**
  - 각 한도의 경계값(같음·초과)을 시험한다.
  - 일 손실 도달 시 킬 스위치가 자동으로 켜진다.
  - 평가 불가 시 주문하지 않는다.
  - 한도를 늘리면 재승인이 필요하다.
- **킬 스위치:**
  - 정지 기록 뒤 제출 직전 재검사로 제출 0건.
  - 해제만으로 재개되지 않고, 재무장이 필요하다.
  - Tauri 테스트: 실행기 프로세스가 종료된다.
- **재시작 복구:** `unknown` 제출이 있으면 조회로 맞추기 전까지 새 주문이 없다. 가짜 서버가 주문을 받았는데 응답이 끊긴 경우를 시험한다.
- **가짜 KIS 모의 서버 종단 시험:** 규칙 전략 1개, 합성 봉, 가짜 응답(접수·거절·부분 체결·호출 한도 오류·토큰 만료)으로 의도 → 제출 → 체결 조회 → 원장 흐름을 확인한다.
- **화면:**
  - Research 빌드 산출물에 모의 주문 화면 모듈이 없다(번들 검사).
  - Agent 빌드에 킬 스위치가 항상 보인다.
  - API 쓰기 엔드포인트가 `siw://app` 출처를 403으로 거절한다.

**수동 확인(P4, 사용자 승인 후):**

- 모의 키·계좌 등록 상태를 확인한다. 계좌번호는 끝 4자리만 본다.
- 토큰 발급 → 잔고 조회 → 지정가 1주 주문 → 체결 조회 → 취소 순서로 진행한다. 응답 필드 이름은 처음 받은 응답으로 확정하고, 문서와 다르면 기록한다.
- 확인 항목: 모의 체결 시각의 의미, 부분 체결 표현, 호출 한도, 국내·해외 모의 지원 범위.

## Alternatives

- **API 프로세스 안에서 주문 루프를 돌린다:** 구조는 단순하지만 API 재시작·오류가 주문 루프와 함께 움직인다. Research 앱도 같은 API를 쓰므로 주문 경로가 공유된다.
- **launchd 상주 실행기:** 앱을 꺼도 계속 돈다. 단계 1에서는 "앱이 열려 있을 때만"이 사용자가 통제하기 쉽다. 운영 기록을 본 뒤 다시 검토한다.
- **실행 중 셸 감지로 화면 분기:** 빌드는 하나로 끝나지만 Research 번들에 주문 화면 코드가 남는다.
- **모의 체결을 `broker_api` 원장에 `environment: demo`로 넣는다:** 표는 줄지만 한 필터만 빠져도 실제 체결과 섞인다. 도메인 규칙(실제/모의 분리)에 어긋난다.
- **시장가 주문 허용:** 모의 서버의 시장가 체결 방식이 미확인이고, 가격 상한을 검사하기 어렵다. 단계 1은 지정가만 제안한다.

## Consequences

- 저장소가 하나(`paper_orders.sqlite3`), 서비스 패키지가 하나(`services/paper_trading`), 계약이 넷 늘어난다.
- Tauri 본체에 Rust 프로세스 관리 코드가 생긴다. 지금의 `lib.rs`는 창만 연다.
- 화면 빌드가 둘이 된다. CI의 빌드 시간이 늘고 Electron 패키징 경로가 바뀐다.
- 모의 체결은 KIS 모의 서버의 시뮬레이션이다. 실거래 체결 품질(슬리피지·부분 체결)을 대표하지 않는다. 화면과 단계 2 검토 자료에 그렇게 적는다.

## 미결 질문(사용자 결정 필요)

1. **첫 시장:**
   - 국내(KRX): 시세는 토스(ADR 0020), 주문은 KIS 모의.
   - 미국: 시세는 Alpaca, 주문은 KIS 해외 모의. 모의 지원 범위는 미확인.
   - 신호 데이터 출처와 주문 증권사가 달라지는 점은 의도에 기록하고 화면에 표시한다.
2. **주문 유형:** 지정가만(제안) 또는 시장가도 허용.
3. **한도 기본값:** 종목 수, 1건 금액, 일 주문 수, 일 손실률.
4. **킬 스위치 기본 동작:** 신규 중지만(제안) 또는 미체결 일괄 취소까지.
5. **실행 시간:** 앱이 열려 있을 때만(제안) 또는 상주.
6. **모의투자 계정:** KIS 모의투자 신청과 모의 앱 키 발급 여부. 사용자만 확인할 수 있다.

## Revisit when

- 미결 질문에 사용자가 답할 때. 이 ADR을 고쳐 accepted로 바꾼다.
- P4 실제 모의 호출에서 문서와 다른 응답 형식·제한이 확인될 때.
- 단계 1 운영 기록으로 단계 2(실계좌, 주문마다 승인)를 검토할 때. 실계좌 차단은 그때 별도 ADR로만 푼다.
