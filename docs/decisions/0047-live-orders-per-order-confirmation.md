# ADR 0047 — SIW Agent 단계 2: 실계좌 주문, 주문마다 사용자 승인

- **Status:** accepted (2026-11-04 사용자 결정)
- **Date:** 2026-11-04
- **Related:** [ADR 0036](0036-desktop-app-roles.md)(주문 Gate), [ADR 0037](0037-paper-order-execution.md)(단계 1 모의 주문), [ADR 0044](0044-paper-protective-orders.md)(보호 청산), [ADR 0029](0029-kiwoom-order-history-sync.md)(키움 조회 전용 동기화·토큰)

## Context

ADR 0036은 주문을 세 단계로 연다. 단계 2는 "실계좌, 주문마다 사용자 승인"이고, 단계 1의 운영 기록을 보고 따로 결정하기로 했다.

**2026-11-04 사용자 결정:**

- 요청: "1부터 시작해줘. 그리고 2까지 진행." 1은 남은 모의 경로 확인(ADR 0044 미확인 항목)이고, 2는 실계좌 단계의 설계와 구현이다.
- 시험 범위: "$100로 1주만 테스트".
- 질문에 대한 답:
  1. 보호 청산(손절·익절·트레일링)도 매번 승인한다.
  2. 하루 주문은 2건까지다.
  3. 승인할 수 있는 시간은 신호 뒤 60초다.
  4. 실계좌 주문에는 키움 실전 키 "Kiwoom1"을 쓴다.

단계 1 운영 기록은 짧다. 실제 모의 서버 확인은 2026-10-23(ADR 0037 P4)과 2026-11-02(ADR 0044)의 두 차례이고, 익절·트레일링·장외 매도·상주 실행기 전체 경로는 아직 미확인이다. 사용자는 이를 알고 단계 2 착수를 정했다. 그래서 단계 2의 첫 실주문 전에 같은 날 모의 확인을 먼저 하는 순서를 지킨다(아래 구현 단위).

**작업 방식의 제약:** 코딩 Agent는 실계좌 주문을 내거나 실계좌 엔드포인트를 시험하지 않는다. 실주문은 사용자가 SIW Agent 화면에서 주문마다 승인 버튼을 눌러야만 나간다. 이 설계는 그 제약과 같은 모양이다.

## Decision

### 1. 모의 경로를 그대로 쓰고, 제출 앞에 승인 대기를 둔다

- 실행기 판단(봉, 신호, 보호, 한도, 킬 스위치, 대조, 체결 동기화)은 단계 1의 `PaperRunner`를 그대로 쓴다. 판단 코드를 둘로 만들지 않는다.
- 다른 점은 제출 단계 하나다. 한도와 킬 스위치를 통과한 의도는 바로 보내지 않고 `awaiting_confirmation`으로 기록한다.
- 사용자가 SIW Agent에서 승인을 누르면, 실행기가 다음 주기에 제출 직전 검사를 다시 하고 보낸다. 다시 하는 검사는 킬 스위치·무장, 미확인 주문, 같은 종목의 열린 주문이다.
- **만료:** 의도를 만든 뒤 60초 안에 승인되지 않으면 `expired`(`not_confirmed`)로 닫는다. 늦게 누른 승인도 받지 않는다. 다음 봉에서 다시 판단한다.
- **거절:** 사용자가 거절하면 `declined`로 닫는다.
- **대기 중:** 같은 종목의 승인 대기 의도가 있으면 새 신호와 보호 청산을 내지 않는다(열린 주문과 같게 본다).
- **보호 청산(결정 1):** 진입과 같이 승인을 받는다. 승인하지 않으면 팔지 않는다. 자리를 비우면 손절이 늦거나 나가지 않는다. 승인 화면과 이 ADR에 위험으로 적는다.
- **취소와 조회:** 미체결 주문 취소(ADR 0044 G1)와 당일 주문 조회는 승인 없이 나간다. 새 위험을 만들지 않고 사용자가 승인한 주문을 정리하는 요청이기 때문이다. 킬 스위치가 켜지면 취소도 하지 않는 기존 규칙은 그대로다.
- **가격:** 승인 시점에 가격을 다시 계산하지 않는다. 의도에 적힌 지정가(시장가 의도는 기준가 ± 버퍼의 지정가)로 보낸다. 지정가라 그보다 불리하게 체결되지 않는다. 60초 만료가 오래된 가격을 막는다.

### 2. 별도 원장

- 실계좌 의도·제출·체결은 `SIW_DATA_DIR/live_orders.sqlite3`에 둔다. 모의 원장(`paper_orders.sqlite3`)과 파일이 다르고, 킬 스위치·무장 상태도 따로다.
- 문서 모양은 모의와 같고 `environment`가 `real`이다. 체결 문서의 `ledger`는 `broker_live_orders`다.
- 저장소는 자기 환경과 다른 `environment`의 문서를 거부한다. 모의 원장에 `real`이, 실계좌 원장에 `demo`가 들어갈 수 없다.
- **실제 체결 원장과의 관계:** 실계좌 체결의 기준 원장은 지금처럼 키움 조회 전용 동기화(ADR 0029)가 채우는 증권사 API 체결 원장이다. `live_orders.sqlite3`의 체결 기록은 실행기가 보호 상태와 대조에 쓰는 자기 기록이다. 두 기록을 합치거나 서로 덮지 않는다.

### 3. 실계좌 도메인은 별도 모듈에만

- 실계좌 adapter는 `services/live_trading/`에 둔다. `api.kiwoom.com` 상수는 이 모듈의 한 곳에만 있다.
- `services/paper_trading/`의 정적 검사(`scripts/check_paper_only.py`)는 그대로다. 모의 코드에는 여전히 실전 도메인이 나타날 수 없다.
- `LiveOnlyClient`는 `PaperOnlyClient`와 같은 규칙이다. 요청마다 host 전체를 비교하고, 리다이렉트를 따르지 않으며, 같은 api-id 허용목록(토큰, 매수, 매도, 취소, 당일 주문)만 보낸다. 다른 host나 api-id면 아무것도 보내지 않고 오류를 낸다.
- 키 환경이 `real`인 키만 받는다. `demo` 키를 주면 생성 단계에서 거부한다.
- 주문 형식은 공식 스펙상 모의와 같다(같은 api-id, 같은 본문). 지정가(`00`)만 쓴다. 실전에서 되는 시장가(`03`)와 장외 주문은 이번에 열지 않는다.

### 4. 한도

- **1건 금액:** 미국 주문은 달러 한도를 새로 둔다(`max_order_amount_usd`). 이번 승인 기본값은 $100이다. 수량 × 지정가로 비교하며 환율이 필요 없다. 값을 넣을 때만 승인 내용에 들어가, 이전 모의 승인의 승인 ID는 바뀌지 않는다.
- **하루 주문 수:** 2건(결정 2). 승인에 필수다.
- **보호 청산과 한도:** 모의와 같이 보호 청산은 한도에 걸려도 기록하고 낸다(ADR 0044 결정 2). 다만 실계좌에서도 사용자 승인은 받는다.
- 실계좌 승인은 달러 한도와 하루 주문 수 없이는 만들 수 없다.

### 5. 키와 토큰

- 실계좌 주문은 사용자가 고른 실전 키 1개(이번에는 "Kiwoom1")만 쓴다. 계좌 참조는 `kiwoom-<sha256(app_key)[:16]>-real`이다.
- 키움 토큰은 클라이언트 하나에만 유효할 수 있다(ADR 0029). 실계좌 실행기가 무장된 동안은 같은 키의 조회 전용 동기화를 API가 거절한다(409). 모의 키만 쓰는 모의 실행기와는 겹치지 않는다.

### 6. 실행 구조와 화면

- **실행기:** `uv run python -m services.live_trading.service`. 모의 실행기와 다른 프로세스이고, 다른 사용자 서비스 라벨(`com.pensivetraveler.siw.agent.live-runner`)이다. 무장과 승인 없이는 heartbeat만 쓴다.
- **API:** `/v1/live/*`. 모의와 같이 시작·승인 쪽 쓰기는 SIW Agent 출처만 받고, 멈추기(`kill`, `disarm`)는 누구나 할 수 있다. 주문 엔드포인트는 없다.
  - 주문별 승인(`POST /v1/live/intents/{id}/confirm`, `decline`)도 SIW Agent 출처만 받는다.
- **화면:** SIW Agent에 "실계좌" 탭을 둔다.
  - 위쪽 띠는 붉게 "실계좌 — 실제 주문"이다.
  - 실행 승인(전략·종목·실전 키·달러 한도·하루 주문 수), 무장, 킬 스위치가 있다.
  - 승인 대기 주문마다 종목·방향·수량·지정가·사유·남은 시간과 승인·거절 버튼을 보인다.
  - 의도·제출·체결 목록이 있다.
- **출처 헤더의 한계:** 출처 헤더는 로컬 프로세스가 꾸밀 수 있다(ADR 0037 §6). 웹 페이지와 Research 앱을 막는 장치일 뿐이고 인증이 아니다. 단계 3 전에 다시 본다.

## 구현 단위

1. **L1:** 저장소·실행기·adapter·API·정적 검사·시험. 가짜 키움 서버(`httpx.MockTransport`)로만 시험하고, 실계좌 도메인으로는 아무것도 보내지 않는다.
2. **L2:** SIW Agent "실계좌" 탭과 상주 실행기 설치.
3. **L3:** 첫 실주문. 같은 날 모의 확인(ADR 0044 미확인 항목)을 먼저 한다. 그 뒤 사용자가 SIW Agent에서 직접 실행 승인·무장하고, 첫 주문의 승인 버튼도 직접 누른다. 코딩 Agent는 그 전후의 원장·로그·체결 조회 기록만 읽어 확인한다.

## Alternatives

- **실계좌용 실행기를 새로 만든다:** 판단 코드가 둘이 되어 모의 확인이 실계좌의 근거가 되지 못한다.
- **모의 원장에 `environment`만 바꿔 같이 둔다:** 원장 분리 규칙(AGENTS.md)에 어긋나고, 킬 스위치를 따로 걸 수 없다.
- **보호 청산은 자동:** 사용자가 고르지 않았다. 단계 3에서 다시 본다.
- **승인 때 가격을 다시 계산:** 사용자가 본 주문과 나가는 주문이 달라진다. 만료를 짧게 두는 쪽을 택했다.

## Consequences

- 자리를 비우면 진입도 청산도 나가지 않는다. 보유 중 손절이 늦어질 수 있다.
- 실행기 주기(10초)만큼 승인 뒤 제출이 늦다.
- 첫 실주문 전까지 실계좌 adapter는 가짜 서버로만 시험된다. 실전 서버의 응답, 체결 시각 형식, 호출 한도는 첫 주문에서 확인한다.

## Revisit when

- 첫 실주문 결과가 나왔을 때(실전 응답 형식, 체결 시각).
- 단계 3(실계좌, 한도 안 자동)을 검토할 때. 그 전에 출처 헤더 대신 앱 안의 확인 경로를 둔다.
- 장외 주문이나 시장가를 실계좌에서 쓰려 할 때.
